# 修复「按质检时间排序」时间不显示 + 第二次查询无反应

## 需求场景

「查询新→旧（质检通过时间）」有两个问题：

1. **时间不显示**：首次按该排序查询时，`reviewed_at` 列全是空（显示 `-`）。
2. **第二次点查询没动静**：再点查询看不到任何变化，必须刷新整个网站才能看到时间。

## 根因分析

`query_images` 的 `sort=reviewed_desc` 分支用的是「只读缓存 + 后台补」的非阻塞设计：

- 它只从 `get_cached_reviewed(pid)` 读缓存（首次为空），立即返回结果，`reviewed_at` 全空。
- 然后调 `preload_reviewed_async(pid)` 在后台补时间。

但 `fetch_reviewed_at()` **只在全部拉取完成后才 `cache_set` 一次**，拉取过程中缓存对其它请求不可见。而且后台并发只有 `REVIEW_CONCURRENCY=4`，几千张要拉很久。于是：

- 第一次查询 → 时间空，后台慢慢拉。
- 第二次查询 → 缓存仍空，结果和第一次一模一样（没变化）→「没动静」。
- 只有等后台全部拉完（或很久后刷新）缓存才有值，时间才显示。

## 处理逻辑

1. **让排序查询同步补齐时间**（`query_images` 的 `sort=reviewed_desc` 分支）
   - 先算出结果中缺失 `reviewed_at` 的非 pending 图 `missing`。
   - 若 `missing` 非空，改为**同步**调用 `fetch_reviewed_at(pid, missing, max_workers=SORT_CONCURRENCY)`，等拉完后再读缓存。
   - 再给每条结果填 `reviewed_at`，然后排序返回。
   - 效果：响应里时间一定是完整的，第一次查询就能显示时间，第二次查询也能立刻返回带时间的结果（已缓存，秒出）。

2. **缓存原地共享、进度即时可见**（`fetch_reviewed_at`）
   - 进入函数后先把 `cached` dict 通过 `cache_set` 挂进缓存（共享引用），再在循环里原地填充。
   - 效果：并发/后台预加载的进度能被后续读取看到，且排序查询的 `need` 计算会自动跳过已拉到的图，避免重复拉取。

3. **并发可调**
   - `fetch_reviewed_at` 增加可选参数 `max_workers`（默认 `REVIEW_CONCURRENCY=4`）。
   - 新增常量 `SORT_CONCURRENCY = 8`，仅供「排序查询」这种用户主动等待的路径使用，比后台预加载快，但仍是有限的一次性开销。
   - 后台预加载仍用 `REVIEW_CONCURRENCY=4`，持续压力不变。

## 架构与技术方案

- 排序查询从「非阻塞秒出但时间空」改为「阻塞补齐后返回完整时间」，可预期、符合用户点击查询即得结果的预期。
- 缓存从「拉完一次性写入」改为「原地共享渐进写入」，同时解决进度不可见与重复拉取问题。
- 平台压力：排序是用户主动触发的**一次性**突发，只在缺时间时发生；持续型后台刷新仍保持 30s / 并发 4 不变。

## 受影响文件

  - 顶部常量区：新增 `SORT_CONCURRENCY = 8`。
  - `fetch_reviewed_at()`（约 line 270）：增加 `max_workers` 参数；循环前先 `cache_set` 共享 dict。
  - `query_images()` 的 `sort=reviewed_desc` 分支（约 line 332-343）：同步 `fetch_reviewed_at` 补齐 missing，再读缓存赋值排序。

## 边界条件与异常处理

- `missing` 为空（已全部缓存）：直接读缓存返回，秒出，不发请求。
- 只有 pending 图缺时间：pending 本身无质检时间，不拉取，排序时排最后。
- 并发调用同一项目：共享 dict 使 `need` 自动去重，重复拉取量最小；dict 赋值原子，无正确性问题。
- 首次「查全部图」排序冷启动：需同步拉取几千张，可能耗时较久，前端已有「首次会拉取质检时间，请稍候…」提示。

## 预期结果

- 第一次点「新→旧」排序：等待（有提示）后返回带完整时间的结果，时间列不再空。
- 第二次点查询：秒出带时间的结果，不再「没动静」。
- 后台持续请求压力不回弹（30s 刷新 + 并发 4 保持）。
